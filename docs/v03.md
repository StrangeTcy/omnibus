# Omnibus V0.3 — evidence-backed recommendations

## What changed, in the existing vertical slice

- Preserved local scanner, typed n-ary graph, provenance/review/correction,
  progress, browser worker, serialized runtime and feedback storage.
- Added provider-independent public search and page verification. The default
  `PublicSearch` retrieves DuckDuckGo HTML using a bounded anonymous public HTTP
  fetcher; `SearchBackend` and the fetcher are replaceable. No paid API, model,
  Ollama installation or Codex dependency is needed for this capability.
- Search snapshots, destination snapshots, reported metadata, retrieval times and
  failure reports persist in existing artifacts; resources and text units use the
  existing graph. No scheduler/new database architecture.
- Graph-based comparison exposes shared and additional represented concepts with
  evidence. Recommendations now include why-now, encountered/current ideas,
  possible additions, actual URL, link-verification state, quotes and uncertainty.
- Semantic findings can also propose explicitly quoted interview guests. They are
  source-backed hypotheses, not inferred identity facts. Analyze related material
  together: cross-batch automatic concept/person reconciliation remains absent.
- Added per-run acceptance observations, including a separate client rendering
  acknowledgement. Composer accessibility alone no longer passes the account stage.

See [audit before changes](v03-audit.md) and the separate
[real-account operator acceptance procedure](v03-operator-acceptance.md).

## Use it

1. Scan accessible book files or import actual supplied transcript text in `/life`.
2. Select relevant content units, authorize your configured browser provider,
   analyze together, inspect quotes, and review/correct proposals.
3. Record actual progress. Compare confirmed coverage under Discovery & comparison;
   Today uses the same confirmed evidence to show a sparse recommendation.
4. To discover a resource, select the current source/interest or liked interview,
   preview the graph-derived public query and authorize network retrieval. Inspect
   the resulting snapshots. Search cannot establish guest identity or equivalence.
5. Analyze the retrieved text with your supplied material, or explicitly propose
   a quoted connection in the discovery card. Review it before it can support a
   recommendation. Manual connections are labeled as such, not called discovered.
6. Accept/dismiss/defer/ignore; feedback persists and is scoped to that candidate.

CLI additions (stop the server first, as with other offline mutations):

```sh
par life discover FOCUS_NODE_ID --query "Crab Canon recording" --authorize-network
par life discover FOCUS_NODE_ID --url "https://example.org/actual-resource" --authorize-network
par life compare SOURCE_NODE_ID CANDIDATE_NODE_ID
```

The URL above is a placeholder, not a discovered recording. For supplied-but-not-
retrieved URLs, use the existing manual Add resource workflow; they are visibly
**manual/unverified**. No network requests happen as a side effect of scanning,
reading progress, recommendation refresh, comparison or graph import.

API additions (existing authentication and CSRF boundary applies):

- `GET /api/life/discovery/context/{id}` — local query proposal; no network.
- `POST /api/life/discovery` — `{focus_id, query?, url?, authorize_network:true}`.
- `GET /api/life/discovery-reports` — last ten persisted result/failure reports.
- `GET /api/life/discovery/{resource_id}/evidence` — intact retrieved snapshot.
- `POST /api/life/discovery/{resource_id}/propose` — `{target_id, relation, quote}`;
  only a provisional `covers`, `illustrates` or `features_person` relationship.
- `GET /api/life/comparison?source=ID&candidate=ID` — confirmed coverage, paths,
  source progress and explicit scope limitations.
- `POST /api/life/recommendations/{id}/rendered` — client DOM acknowledgement;
  only currently eligible recommendations accepted.

## Trust and limits

The public fetcher uses HTTP(S) standard ports, no cookies/proxy environment,
certificate verification, a DNS-pinned public destination, and rechecks every
redirect. Private, loopback, link-local, multicast, reserved and mixed DNS targets
are refused. At most three result candidates, four requests per redirect chain,
2 MiB per response, and a 25-second network budget per fetch. OS DNS resolution
uses the system resolver and can outlive that budget; this is not a hostile-network
process sandbox. Compressed responses/media downloads are refused; no JavaScript
execution, anti-bot bypass, account automation or provider fallbacks.

The parser retains up to 60,000 characters of extracted webpage text; the first
12,000 become selectable 2,000-character units. It is not a media transcription
service. Title and unambiguous `datePublished`/publication meta values are reported
metadata, not independently corroborated facts. Some otherwise usable pages will
be rejected (including JS-only, login/challenge pages and pages without a title).

A discovered resource is recommendation-eligible only with intact retrieval
artifacts and quoted, confirmed relationship support. Guest recommendations also
require a name/known-alias-bearing retrieved quote. Dates, identities and semantic
interpretations still have explicit uncertainty; a page may be wrong. Arbitrary
model-generated URLs without retrieval are withheld, not relabeled manual.

Correcting the URL/title/date invalidates the old retrieval association. Graph-only
imports lack raw artifact proof and cannot promote discovery flags into verified
status. Full runtime backups retain snapshots and stage histories. No live database
sync, account-cookie export, or required native browser download was added.

Local tests use **synthetic provider/network fixtures**, including composition +
functor comparison, recording and newer-guest paths, failure handling and actual
DOM rendering through JSDOM. They prove local plumbing, not model reasoning or
live website selectors. Optional DOM setup uses the existing testing convention:

```sh
npm install --prefix .cache/life-dom --no-package-lock jsdom@26
python -m pytest -q
```

JSDOM is optional, not an application dependency or a real Chrome visual test.
Real-account acceptance remains on the user's machine. See operator checklist for
exact stage evidence and how not to overclaim success.
